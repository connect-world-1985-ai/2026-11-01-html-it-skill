    Findings by severity

    High, blocks merge F001 refresh token in localStorage

    Location: auth/session.ts:88

    The refresh token is written to localStorage. Any script that runs on the page can read it there, including a script injected through a cross-site scripting bug, and a stolen refresh token lets an attacker keep creating new sessions for that user. SEC-12 no tokens in web storage forbids exactly this.

    Fix: move the refresh token out of web storage, as the security rule requires. The review summary does not say where it should live instead; an HttpOnly cookie is the usual choice, to be confirmed with the author.

    Medium F002 retry loop without backoff

    Location: not given in the review summary.

    The retry loop tries again without any backoff. This matches INC-2291 login outage on 14 September 2026, which was caused by retry storms: many clients retrying at once kept the login down.

    Fix: add a growing wait between retries, so a failing refresh cannot turn into a retry storm.

    Low F003 log line leaks user email

    Location: auth/session.ts:131

    A log line writes the user's email address into the logs, where anyone with log access can read it.

    Fix: remove the email from the log line.

    Glossary

    Backoff
    Waiting longer between each retry, usually doubling the wait, so that many clients do not retry at the same moment.
    HttpOnly cookie
    A cookie the browser sends with requests but that page scripts cannot read.
    localStorage
    Browser storage (one kind of web storage) that any script running on the page can read, including injected scripts.
    Refresh token
    A long-lived credential the app uses to get new short-lived session tokens without asking the user to sign in again.
    Retry storm
    A failure mode in which many clients retry at the same time and the extra load keeps the service down.
