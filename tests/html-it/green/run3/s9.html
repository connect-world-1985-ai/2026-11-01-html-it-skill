Incident postmortem

    Booking API slowdown, 29 October 2026

    On 29 October 2026 booking was slow or failing for 29 minutes (09:12 to 09:41 CET); about 1,140 booking attempts failed and no data was lost. The cause was a missing database index: the new appointment search from PR 402 new appointment search query shipped without its index migration, so every search scanned the whole slots table and used up the database connection pool. Rolling back to the previous release fixed it. Three follow-up actions are open: add the index by 5 November, load-test search by 14 November, and add a CI check that catches full table scans by 28 November 2026.

    What caused it

    Release 8.4.0.0 contained the new appointment search query from PR 402 new appointment search query. That query filters the slots table by practice and start time, which needs an index on slots(practice_id, start_time). The index was in the migration plan, but the migration file that creates it was not part of the pull request, so the release went out without it.

    Without the index, the database had to read the whole slots table for every search request (a full table scan). These slow queries held database connections much longer than usual, until all 50 connections in the connection pool were busy. New booking requests then had to wait for a free connection, which pushed latency up and made requests fail.

    The process gap is that nothing between the pull request and production noticed the missing migration: review did not catch it, and load test LT-12 booking load test does not exercise search, so it could not show the slowdown before release.

    What went well and what did not

    Went well

    • The alert fired within 2 minutes.
    • Rollback runbook RB-04 rollback runbook worked as written.

    Went badly

    • Load test LT-12 booking load test does not cover search, so the slow query was not caught before release.
    • The index was in the migration plan, but the migration file was missing from the pull request, and nothing checked for it.

    Glossary

    Blameless postmortem
    A postmortem format that looks for gaps in process and tooling, not for a person to blame.
    p95 latency
    The 95th percentile of response time: 95 % of requests were faster than this value.
    Full table scan
    The database reads every row of a table because no index lets it jump to the matching rows.
    Connection pool
    A fixed set of open database connections (here 50) that the service shares between requests; when all are in use, new requests wait.
    CI
    Continuous integration: the automated build and checks that run on every pull request.
