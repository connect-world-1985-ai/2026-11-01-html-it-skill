Incident postmortem

    Booking API slowdown on 29 October 2026

    For 29 minutes on 29 October 2026 (09:12 to 09:41 CET), booking was slow or failed: about 1,140 booking attempts failed and no data was lost. The cause was a missing database index: release 8.4.0.0 shipped a new appointment search query whose index migration was planned but left out of the pull request, so every search read the whole table and used up the database connections. Rolling back to 8.3.2.4 ended it. Three actions close the gaps; the index migration is due first, on 5 November 2026.

    What happened

    The process gap was in how the change reached production, not in any one person's work. The migration plan for the new appointment search included an index on slots(practice_id, start_time), but the migration file that creates it was not part of PR 402 new appointment search query. Nothing in the pipeline caught the omission: load test LT-12 booking load test does not exercise search, so the slow query never ran under load before release 8.4.0.0 went live.

    Without the index, the database has to read every row of the slots table to answer each appointment search, which is called a full table scan. Each scan holds a database connection far longer than a normal query. With searches arriving all the time, all 50 connections in the pool were soon busy, and every other booking request, not only search, had to wait for one. That is why the whole booking API slowed down and some bookings failed.

    What went well

    • The alert fired within 2 minutes, so the on-call engineer knew about the problem almost at once.
    • Rollback runbook RB-04 rollback runbook worked exactly as written; the rollback took 7 minutes from start (09:34 CET) to normal latency (09:41 CET).

    What went badly

    • Load test LT-12 booking load test does not cover search, so a slow search query can reach production without being seen under load.
    • The index was in the migration plan, but the migration file was missing from PR 402 new appointment search query. Neither review nor any automated check noticed that the plan and the pull request did not match.

    Glossary

    Blameless postmortem
    A review of an incident that looks for gaps in process and tooling, not for a person to blame.
    CI (continuous integration)
    The automated build and checks that run on every pull request.
    Connection pool
    A fixed set of open database connections that requests share; when all are in use, new requests wait.
    Full table scan
    Reading every row of a table to answer a query, because no index narrows the search.
    Index
    A database structure that lets a query find matching rows without reading the whole table.
    Migration
    A versioned script that changes the database schema, for example by adding a table or an index.
    On-call engineer
    The engineer assigned to respond to alerts during a given period.
    p95 latency
    The response time that 95 % of requests stay under; the slowest 5 % take longer.
    Query plan
    The database's description of how it will run a query, for example whether it uses an index or scans the table.
    Rollback
    Returning the production system to the previous release.
