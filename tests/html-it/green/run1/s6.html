Backend onboarding: order service

    Event sourcing in the order service

    The order service does not store an order as one row that gets overwritten. It stores every change to the order as an event in a log that only ever grows, and it works out the current order by replaying those events. The team chose this in ADR-007 decision to use event sourcing for orders (March 2025) because medical billing needs a full audit trail. Before your first change, read the flow diagram, step through the example order, and learn the three costs this design brings.

    Prepared 3 November 2026 for backend engineers joining the order service team, especially those who have mostly built CRUD backends.

    A snapshot versus a log

    In a CRUD backend, an order is one row in an orders table. When the payment arrives, an UPDATE changes the status column, and the previous value is gone unless someone wrote it to a separate history table. The row tells you what the order looks like now and nothing about how it got there.

    With event sourcing, the order service writes each change as a new entry in an append-only log: OrderPlaced, then PaymentCaptured, then OrderShipped. Nothing is overwritten. The current state of an order is the result of reading its events from the first to the last and applying each one. That reading is called a replay.

    QuestionCRUD rowEvent log
    What is stored?The latest values onlyEvery change, in order
    What happens on a change?The row is overwrittenA new event is appended
    Where does the current state come from?Reading the rowReplaying the events
    Can you see the order as it was last week?Only with extra history tablesYes, replay up to that date

    How a change flows through the system

    Writing and reading are split into two sides. The write side decides whether a change is allowed and records it as an event. The read side turns events into tables shaped for the screens that need them.

    1. A command asks for a change, for example "capture the payment for this order". A command can still be refused.
    2. The aggregate for that order replays the order's events to know its current state, checks the business rules (a rule might say, for example, that a shipped order cannot be cancelled) and, if the command is allowed, produces one or more new events.
    3. The event store appends those events to the order's log. From this moment the change is a fact.
    4. A projector picks up the new events and applies them to the tables it maintains. The result is called a projection.
    5. A read model such as the order list or the invoice view now holds the data in exactly the shape a screen needs.
    6. The user interface reads from the read models, never from the event log directly, and the user's next action becomes the next command.

    3OrderShipped2026-03-03Shipped Paid and shipped

    To answer "what did this order look like on 1 March 2026?", the service replays only the events dated up to 1 March: events 1 and 2. The answer is "paid, not yet shipped", even though the order has shipped since. This is a temporal query, and a CRUD row cannot answer it, because it only knows the latest status.

    Why the team chose event sourcing

    The architecture decision record ADR-007 decision to use event sourcing for orders, written in March 2025, gives three reasons.

    A full audit trail for medical billing. Billing for medical services has to show who changed what and when. With event sourcing that history is not an extra log that can drift out of step with the data; it is the data. Every state the order ever had can be shown and explained.

    Read models are easy to rebuild. Because every read model is derived from the events, a broken or outdated read model can be deleted and rebuilt by replaying the log through its projector. A new screen that needs the data in a new shape gets a new projection, filled from the full history, without a data migration on the write side.

    Temporal queries. As in the example above, the service can show an order as it was on any past date by replaying events up to that date.

    What it costs

    Event sourcing makes some things harder. These three costs come up in everyday work on the order service.

    Event schemas must be versioned

    Events are stored forever and never rewritten, so an event written in March 2025 must still be readable by the code you deploy today. When you change the shape of an event, for example by adding a field to PaymentCaptured, the code has to handle both the old and the new shape. This is event schema versioning. You cannot fix a bad event by editing it; you append a new event that corrects it.

    Read models lag slightly behind

    The projector updates read models after the event is stored, not in the same transaction. For a short time, the order list can still show the old status after a payment has been captured. This is eventual consistency. Code that has just sent a command should not expect the read model to show the result immediately.

    Replay time grows with history

    An order with a long history means a long replay each time the aggregate loads it. To keep loading fast, the order service saves a snapshot every 500 events. Loading then starts from the latest snapshot and replays only the events after it, so no load replays more than 499 events.

    Check yourself

    A customer cancels a paid order. Do you update the order's status?

    No. The aggregate checks whether cancelling is allowed and, if so, appends a new event that records the cancellation. The status shown on screen changes because the projector applies that event to the read models.

    The invoice view shows wrong totals for old orders because of a bug in its projector. How is it fixed?

    Fix the projector, then rebuild the invoice view by replaying the events through it. The events themselves were correct, so nothing on the write side changes.

    Right after a payment is captured, a test reads the order list and still sees "not paid". Is that a bug?

    Not necessarily. Read models are eventually consistent, so the projector may not have processed the new event yet. The test should wait for the projection to catch up instead of expecting it instantly.

    Glossary

    Aggregate
    The object that owns one order's rules. It rebuilds the order from its events, checks a command against the rules, and emits new events.
    Append-only log
    A store where new entries are only added at the end; existing entries are never edited or removed.
    Command
    A request to change something, such as "capture the payment". It can be rejected.
    CRUD
    Create, read, update, delete: the usual style where each record is one row and an update overwrites it in place.
    Event
    A fact about something that already happened, named in the past tense, such as OrderPlaced. Events are never changed or deleted.
    Event schema versioning
    Managing changes to an event's structure so that old events already in the log can still be read by new code.
    Event sourcing
    Storing every change to an entity as an immutable event, and deriving its state by replaying those events in order.
    Event store
    The database that holds the append-only log of events for every order.
    Eventual consistency
    Read models will match the event log once the projector has processed the latest events, but not necessarily at the same instant.
    Projection
    A read model built from events by a projector; the term is often used for the projector and its table together.
    Projector
    A component that reads events from the event store and updates one read model from them.
    Read model
    A table or document shaped for one screen or query, such as the order list or the invoice view. It is derived from events and can be rebuilt.
    Replay
    Reading an entity's events in order and applying each one to rebuild its state.
    Snapshot
    A saved copy of an aggregate's state at a certain event, so a replay can start there instead of at the first event. The order service takes one every 500 events.
    Temporal query
    A question about the state of something at a past point in time, answered by replaying events only up to that time.
