    How a booking request flows through the code

    A booking request enters at BookingResource, and BookingService.book() does the real work: it locks the slot in Redis, checks that the slot is still free, saves the booking and publishes a BookingCreated event, which the SMS service uses to schedule the reminder. Before changing this path, Priya should know three rules that prevent double bookings: keep the lock's lifetime longer than the database timeout, let a taken slot surface as HTTP 409, and never call book() from inside another transaction.

    Prepared on 3 November 2026 for Priya, who is joining the booking team. The code shown is BookingService.java on the master branch at commit 7c41e9a the version this walkthrough describes.

    The request path, step by step

    One request touches five classes in the booking service and then leaves the service as an event. The slot lock is the part that matters most: it is held from the moment the slot is checked until the event is published, so no other request can book the same slot in between.

    1. Receive the request. BookingResource.java handles POST /bookings and turns the request body into a BookingRequest.
    2. Run the booking logic. The resource calls BookingService.book(), the method shown in full below.
    3. Lock the slot. SlotLock.acquire(slotId) takes a Redis lock on that one slot. The lock has a time to live (TTL) of 30 seconds, so a crashed request cannot block the slot for longer than that.
    4. Check availability. With the lock held, slots.findAvailable() looks the slot up again. If someone booked it in the meantime, the method throws SlotTakenException, which the caller receives as HTTP 409.
    5. Save. BookingRepository.save() writes the new booking to the database.
    6. Publish. BookingEventPublisher.publish() sends a BookingCreated event carrying the new booking's ID.
    7. Remind. The separate sms-service receives the event and schedules the reminder text message. It does not run inside book(), so a slow SMS provider does not slow down the booking.

    The key method: BookingService.book()

    The whole booking happens inside one try-with-resources block. Closing the block releases the slot lock, whether the booking succeeded or failed.

    1public Booking book(BookingRequest req) {
2    try (SlotLock lock = slotLock.acquire(req.slotId())) {
3        Slot slot = slots.findAvailable(req.slotId())
4            .orElseThrow(() -> new SlotTakenException(req.slotId()));
5        Booking booking = repository.save(Booking.from(req, slot));
6        events.publish(new BookingCreated(booking.id()));
7        return booking;
8    }
9}

    Line 2. The lock is taken before anything is read, so two requests for the same slot run one after the other, never side by side.

    Lines 3 and 4. The availability check happens under the lock. A check before the lock would be useless: another request could book the slot between the check and the lock.

    Lines 5 and 6. Save first, then publish, so the event never announces a booking that was not stored.

    Line 8. The end of the block closes lock and releases the slot, also when line 4 throws.

    Line numbers count from the start of this excerpt, not from the top of BookingService.java.

    Three rules that keep bookings safe

    1. The lock must outlive the database timeout

      The Redis lock expires after 30 seconds, and that lifetime must stay longer than the database timeout. If the lock ran out while save() was still waiting on the database, a second request could take the lock, find the slot still free and book it as well. The team recorded this rule in ADR-011 Redis slot locks. The current database timeout is not stated in this walkthrough; check its configured value before changing either number.

    2. A taken slot becomes HTTP 409

      SlotTakenException is translated into HTTP 409 Conflict in ExceptionMappers.java. The client then knows the slot is gone and can offer another one. Throw this exception for a taken slot rather than returning an error by hand, so every caller gets the same response.

    3. Never call book() inside another transaction

      Calling book() from code that already has a database transaction open caused the double bookings in BUG-3120 double bookings, June 2026. The code above shows why this is dangerous: the lock is released when book() returns, but if an outer transaction has not committed yet, the new booking is not yet visible. A second request can then take the lock, still see the slot as free and book it again. This explanation follows from the code; the bug ticket itself was not part of the material for this page.

    Glossary

    Redis lock
    A short-lived key in Redis that only one request can hold at a time; other requests for the same key must wait or fail.
    Time to live (TTL)
    How long Redis keeps a key before deleting it on its own. For the slot lock it is 30 seconds.
    Try-with-resources
    A Java statement, try (Resource r = …) { … }, that closes the resource automatically when the block ends, also when an exception is thrown.
    BookingCreated event
    A message saying that a booking was created; other services, such as sms-service, react to it.
    sms-service
    The service that sends text messages to customers; it schedules a reminder when it receives BookingCreated.
    HTTP 409 Conflict
    The HTTP status code for a request that conflicts with the current state of the resource, here a slot someone else already booked.
    Transaction
    A group of database changes that become visible to other requests together, only when the transaction commits.
