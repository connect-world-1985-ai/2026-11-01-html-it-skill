Pull request write-up

    Paginate booking search

    PR 437 Paginate booking search replaces OFFSET pagination in the booking search with keyset pagination on (start_time, id) and adds a matching database index, so deep pages stay fast instead of slowing down after page 50. One behaviour changes for clients: the search response no longer contains a total count. Review the query change in BookingSearchService.java first; it is shown below with notes.

    Branch feature/KT-948-pagination into master, for KT-948 booking search slow on large practices. Prepared 3 November 2026 for the reviewers of the pull request.

    The reason is speed and safety. With OFFSET pagination the database reads and throws away every row before the requested page, so with the default of 20 slots per page, page 50 reads about 1,000 rows to return 20. INC-2307 booking outage of 29 October 2026 showed what a full table scan on this data does to the booking API.

    The key change

    The whole pagination logic of the search is this one statement in booking-api/src/main/java/com/example/booking/BookingSearchService.java. Removed lines start with -, added lines with +.

    -    return query.offset(page * size).limit(size).fetch();
+    return query.where(cursor.after(lastStartTime, lastId))
+                .orderBy(SLOT.START_TIME.asc(), SLOT.ID.asc())
+                .limit(size + 1).fetch();

    Removed line. The old query skips page * size rows. Its cost grows with the page number, which is the slowdown reported in KT-948 booking search slow on large practices.

    The cursor condition. The new query starts right after the last slot of the previous page, identified by its start time and ID. The database can jump there through the index instead of counting rows, so page 50 costs about the same as page 1.

    The sort order. Slots are sorted by start time, and by ID when two slots start at the same time. The ID makes the order unique, which is what keeps pages from repeating or skipping slots; one of the new tests checks exactly this.

    One extra row. The query fetches size + 1 rows. The excerpt does not show what happens to the extra row; check in the full diff that it only decides whether a nextCursor is returned and is not sent to the client as part of the page.

    The new migration V57__search_index.sql adds an index on slots(practice_id, start_time, id). Its columns follow the query: the search filters by practice and then reads slots in start-time and ID order, so the page can be read straight from the index without a full table scan.

    Risk: the total count is gone

    Keyset pagination does not count the rows it skips, so the pull request removes the total count from the search response. Mobile app 3.2 reads that field only to show a label; the app team confirmed this.

    Open point: the write-up names no other client of the booking search. If you know of a client that relies on the total count, say so in the pull request before it is merged.

    How to test

    1. Run the integration tests

      Run the test class BookingSearchServiceIT in booking-api. All tests should pass, including the six new ones.

    2. Page through a practice by hand

      Against a running booking API, request the first page with five slots per page:

      GET /bookings/search?practice=17&size=5

      Then follow the nextCursor value from each response to the next page. Each page should hold five slots, in start-time order, and no slot should appear twice or go missing between pages. How the cursor is passed back is described in docs/api/booking-search.md; this write-up does not repeat it.

    What to check in review

    • Requests with size above 100: the write-up says the maximum is 100 but not whether larger values are rejected or reduced to 100. See BookingSearchResource.java.
    • The resource now takes a page parameter while the service pages by cursor: check what page still does, so that clients are not offered a parameter that has no effect.
    • The extra row from limit(size + 1) is used only to decide on nextCursor.
    • The index columns in V57__search_index.sql match the filter and sort order of the new query.
    • docs/api/booking-search.md mentions that the total count is gone and explains nextCursor.

    Glossary

    Cursor (nextCursor)
    A value in the search response that marks the last slot of the current page; the client sends it back to get the next page.
    Full table scan
    A query that reads every row of a table because no index fits its filter or sort order.
    Keyset pagination
    Pagination that continues after the last row the client has seen, here identified by start time and ID, instead of skipping a number of rows.
    OFFSET pagination
    Pagination that skips page × size rows and returns the next size rows; the database still reads every row it skips.
