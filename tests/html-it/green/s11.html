    How a booking request flows through the code

    A booking request enters the booking API at POST /bookings, takes a short-lived lock on the requested slot, is saved to the database while the lock is held, and then announces itself with a BookingCreated event so that the sms-service can schedule the reminder. The lock is what prevents double bookings, so the three rules at the end of this page are the ones to keep in mind before changing anything on this path.

    The flow at a glance

    Six parts take part in every booking. Five live in the booking code base; the last one is a separate service that reacts to the event.

    Step by step

    1. The endpoint receives the request

      BookingResource.java exposes POST /bookings. It turns the HTTP request into a BookingRequest and hands it to BookingService.book().

    2. The service takes over

      BookingService.book() is the one place that orders the steps below. Everything that must happen for a booking to be valid happens inside this method.

    3. The slot is locked

      SlotLock.acquire(slotId) takes a slot lock in Redis with a time to live (TTL) of 30 seconds. While one request holds the lock, no other request can book the same slot. The TTL means a crashed request cannot block the slot for longer than 30 seconds.

    4. Availability is checked and the booking saved

      With the lock held, the service checks that the slot is still free and saves the booking through BookingRepository.save(). If the slot is already taken, it throws SlotTakenException instead.

    5. The event is published

      BookingEventPublisher.publish() sends a BookingCreated event carrying the new booking's ID.

    6. The sms-service schedules the reminder

      The sms-service, a separate service, receives BookingCreated and schedules the reminder SMS.

    The key code

    This is the whole of book() in BookingService.java at 7c41e9a master commit. The lock is opened in a try-with-resources block, so it is released automatically when the method returns or throws.

    public Booking book(BookingRequest req) {
    try (SlotLock lock = slotLock.acquire(req.slotId())) {
        Slot slot = slots.findAvailable(req.slotId())
            .orElseThrow(() -> new SlotTakenException(req.slotId()));
        Booking booking = repository.save(Booking.from(req, slot));
        events.publish(new BookingCreated(booking.id()));
        return booking;
    }
}

    Line 2: the lock is acquired before anything is read, so the availability check on lines 3 and 4 cannot race with another request for the same slot. Line 4: a taken slot ends the method with SlotTakenException, and the lock is still released. Lines 5 and 6: the save and the event both happen while the lock is held.

    Three rules to keep

    1. The lock TTL must be longer than the database timeout. This is recorded in ADR-011 Redis slot locks. If a database call could run longer than the 30-second lock, the lock would expire while the first request is still saving, and a second request could book the same slot. The current database timeout is not given in the source; check it before changing either number.

    2. SlotTakenException becomes HTTP 409. ExceptionMappers.java maps it to 409 Conflict, so clients see "slot already taken" rather than a server error.

    3. Never call book() inside another transaction. Doing so caused the double bookings in BUG-3120 double bookings, June 2026. A likely reason, as far as the code shows: inside an outer transaction, the save is not yet committed when the lock is released at the end of book(), so the next request still sees the slot as free. The bug report itself is not included here; read it for the confirmed cause.

    Glossary

    Architecture decision record (ADR)
    A short document that records one technical decision, its reasons and its consequences.
    Slot lock
    A short-lived lock stored in Redis that only one booking request can hold for a given slot at a time.
    Time to live (TTL)
    How long Redis keeps the lock before it expires on its own, even if nobody releases it. For slot locks it is 30 seconds.
    Try-with-resources
    A Java statement that closes the resource automatically when the block ends, whether normally or by an exception.
    Event
    A message announcing that something has happened, here BookingCreated, which other services such as the sms-service react to.
    409 Conflict
    The HTTP status code meaning the request conflicts with the current state of the resource; here, the slot is already booked.
    Transaction
    A group of database changes that are committed together or not at all; other requests do not see them until the commit.
