    Patient portal UI audit

    The UI audit of the R26.11 release of the patient portal found one issue on each of 40 screens. Ten are described here, from a missing password label to an insurance number shown in full; the issues on screens 11 to 40 are still to be written in. Developers: open a screen below, fix its issue, and check the result against the screenshot.

    Prepared 3 November 2026 for the patient portal designers and developers. Priorities and owners are not given in the audit.

    The screenshots are not in this folder yet. The designers' 40 PNG files were not provided with the audit. Each screen page shows a placeholder naming the expected file; once a designer puts the export into assets/, it appears on that page with no rebuild.

    What the audit found

    The insurance number on the profile screen is the only issue that exposes personal data: the audit says it should be masked. Three issues shut out people who rely on assistive technology or cannot distinguish colours: the login password field has no visible label, unread messages are marked only by colour, and settings toggles do not say what on and off mean.

    Two screens are inconsistent within themselves. The dashboard has three competing primary buttons, and the appointments list mixes the date formats 03/11 and 2026-11-03, which can be read as two different days. Cancelling an appointment has no confirmation, so one accidental tap cancels it. Long messages overflow on 390 px wide phone screens. Downloads lack their file size, and a help search without results offers no empty-state guidance.

    Why this is a folder, not one file

    The team prefers single HTML files, and most pages are one file. This audit is an exception for two reasons. The 40 screenshots total about 52 MB; embedded in one HTML file they would grow to about 70 MB, well past the 20 to 25 MB that email attachments usually allow. And the designers keep editing the original PNGs, so copies baked into a page would go out of date with every new export, while files in assets/ are picked up as they change.

    The folder still behaves like one file: it opens offline, needs no server, and every link inside it is relative.

    Adding the screenshots and sharing the folder

    1. Designers: save each export into assets/ next to index.html, using the original file names, for example assets/01-login.png. Replacing a file updates the screen page the next time it is opened.
    2. For screens 11 to 40, send the screen names and issues so that each gets its own page and a row in the table above.
    3. To share, zip the whole folder (index.html, parts/ and assets/). Readers unzip it and open index.html.

    If a single file is required anyway: compressing the screenshots to WebP or JPEG at most 1600 px wide could bring one page to roughly 10 to 20 MB, but its images would stop matching the designers' files after the next export.

    Glossary

    Primary button
    The visually strongest button on a screen, reserved for the one main action the user is expected to take.
    Empty state
    What a list or search result shows when there is nothing to show, ideally with an explanation and a next step.
    Masking
    Showing only part of a sensitive value and hiding the rest, for example only the last few digits of a number.
    Overflow
    Content that is wider than its container and is cut off or forces sideways scrolling.
