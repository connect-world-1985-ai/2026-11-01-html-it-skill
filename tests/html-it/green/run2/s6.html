    Event sourcing in the order service

    The order service does not store what an order looks like now. It stores every change that ever happened to the order, as an event in a log that is only ever added to, and works out the current state by replaying those events. The team chose this in ADR-007 the decision to use event sourcing (March 2025) because medical billing needs a full audit trail. If you come from CRUD backends, the one habit to unlearn is "update the row": here you append a new fact instead.

    Written for backend engineers joining the team. Allow about 15 minutes; the example in the middle is interactive.

    Snapshot versus log

    In a CRUD backend, an order is one row. When it is paid, a column changes from "unpaid" to "paid", and the old value is gone. The row is a snapshot of the present.

    With event sourcing, the order is a list of events: facts in the past tense, such as OrderPlaced, PaymentCaptured and OrderShipped. They live in an append-only log. Nothing is overwritten, so the history is the data, and the present is something you compute from it.

    QuestionCRUD (snapshot)Event sourcing (log)
    What is stored?The current state of the orderEvery change, in order
    How does a change happen?Update the rowAppend a new event
    Where does the current state come from?Read the rowReplay the events (or read a read model built from them)
    What did the order look like on 1 March?Unknown, unless someone kept a history tableReplay the events up to 1 March

    How a change flows through the service

    A change travels in one direction: from a request, through the rules, into the log, and from there out to the screens people use.

    1. A command asks for a change, for example "ship this order". It can still be refused.
    2. The aggregate for that order rebuilds the order from its past events, checks the command against the rules (an order cannot ship before payment is captured, for instance), and decides which new events to record.
    3. The event store appends those events. From this moment the change is a fact.
    4. A projector reads each new event and updates one or more read models, such as the order list and the invoice view. Building a read model this way is called a projection.
    5. The UI reads the read models. It never reads or writes the event log directly.

That is events 1 and 2, so the order was paid but not yet shipped. A query like this, about the state at a past moment, is a temporal query, and with an event log it needs no extra history tables.

    Why the team chose event sourcing

    ADR-007 the decision to use event sourcing, the architecture decision record (ADR) from March 2025, gives three reasons.

    • A full audit trail for medical billing. Billing for medical services has to be able to show who changed what, and when. In an event log that trail is not an add-on that could be forgotten or fall out of sync; it is the data itself.
    • Read models are easy to rebuild. Because every read model is derived from the events, a buggy or outdated read model can be thrown away and rebuilt by replaying the log through a corrected projector. A new screen can get its own read model, filled with the complete history from day one.
    • Temporal queries. Questions such as "what did this order look like on 1 March?" are answered by replaying up to that date, as in the example above.

    What it costs

    The same properties that bring these benefits bring three costs. You will meet all of them in your first weeks.

    Event schemas must be versioned

    Events are never changed after they are written, so an OrderPlaced event recorded in 2025 keeps its 2025 shape for ever. When the shape of an event changes, the code that reads events must still understand every older version. This is event schema versioning, and it replaces the database migrations you may be used to: you cannot rewrite history, so you teach the code to read it.

    The screens lag slightly behind the log

    The projector updates the read models after the event is stored, not in the same step. For a short time the order list can still show an order as "Paid" when it has already been shipped. This is eventual consistency between the write side and the projections. When you build a screen or a test, expect that delay instead of treating it as a bug.

    Replay gets slower as orders collect events

    Replaying three events is instant; replaying thousands is not. To keep it fast, the order service takes a snapshot every 500 events. Rebuilding an order then means loading the latest snapshot and replaying only the events after it. Try it:

    Check your understanding

    1. A customer's delivery address on an order was wrong and is corrected. What happens in the event store?

    A new event that records the correction is appended. The earlier event with the wrong address stays in the log, which is exactly what the audit trail needs. Nothing is updated in place.

    2. Right after shipping an order, the order list still shows it as "Paid". Is that a bug?

    Probably not. The projector updates the order list shortly after the OrderShipped event is stored, so a brief lag is expected (eventual consistency). If the list never catches up, look at the projector.

    3. An order has 1,240 events and snapshots are taken every 500 events. How many events are replayed to rebuild it?

    240. The latest snapshot is at event 1,000, so only events 1,001 to 1,240 are replayed.

    4. The invoice view shows wrong totals because of a bug in how it adds them up. How is the data fixed?

    Fix the projector that builds the invoice view, then rebuild that read model by replaying the events. The events themselves were right all along and are not touched.

    Glossary

    Architecture decision record (ADR)
    A short document that records one architecture decision, the reasons for it and its consequences.
    Aggregate
    The object that owns the business rules for one order. It rebuilds the order from its events, checks each command against the rules, and decides which new events to record.
    Append-only log
    A log where new entries are only ever added at the end; existing entries are never edited or removed.
    Command
    A request to change something, phrased as an instruction ("ship this order"). Unlike an event, it can be rejected.
    CRUD
    Create, read, update, delete: the usual style where a table row holds the current state and changes overwrite it.
    Eventual consistency
    Read models match the event log once the projector has caught up, but not necessarily at the same instant.
    Event
    A record of something that has already happened, named in the past tense, for example OrderPlaced. Events are never changed or deleted.
    Event schema versioning
    Managing changes to the structure of an event type so that code can still read every version ever stored.
    Event sourcing
    Storing every change to an entity as an event in an append-only log, and deriving its current state by replaying those events.
    Event store
    The database that holds the append-only log of events for every order.
    Projection
    A read model together with the projector that builds it from the events; the word is used for both.
    Projector
    Code that reads new events from the event store and updates a read model to match.
    Read model
    A table or view shaped for one screen or query (the order list, the invoice view), built from the events by a projector. It can be thrown away and rebuilt.
    Replay
    Applying an order's events one after another, from the first (or from a snapshot), to compute its state.
    Snapshot
    A saved copy of an aggregate's state at a given event, so replay can start there instead of at the first event. The order service takes one every 500 events.
    Temporal query
    A question about what something looked like at a past point in time, answered by replaying events only up to that time.
