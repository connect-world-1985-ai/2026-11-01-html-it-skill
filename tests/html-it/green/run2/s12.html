Pull request write-up

    Paginate booking search

    PR 437 Paginate booking search replaces OFFSET pagination in the booking search with keyset pagination on (start_time, id) and adds a matching index, so that searches on large practices stay fast beyond page 50. One behaviour change needs a reviewer's attention: the search response no longer contains the total count. Please review the service change and the migration, run the checks under "How to review", and approve or comment on the pull request.

    Ready for review Branch feature/KT-948-pagination into master. Five files, +248 −33 lines. Fixes KT-948 booking search slow on large practices.

    The key change

    The whole idea fits in one statement in BookingSearchService.java. The old query told the database to skip page × size rows and return the next size; the new query starts directly after the last row the client has seen.

    -    return query.offset(page * size).limit(size).fetch();
+    return query.where(cursor.after(lastStartTime, lastId))
+                .orderBy(SLOT.START_TIME.asc(), SLOT.ID.asc())
+                .limit(size + 1).fetch();

    Removed line. With OFFSET pagination the database reads and throws away every row before the requested page, so page 50 at size 20 reads about 1,000 rows to return 20. That is why KT-948 slow search appears only after page 50.

    First added line. Keyset pagination: the cursor carries the start time and ID of the last slot on the previous page, and the query continues after that pair.

    Second added line. Ordering by start time and then by ID makes the order total: two slots with the same start time always come out in the same order, so no slot is shown twice or skipped between pages. One of the new integration tests checks exactly this.

    Third added line. The query fetches one row more than the page size. The write-up does not say why; the usual reason is to tell whether a next page exists without a separate count query. To be confirmed by the author.

    Why this change

    Booking search on large practices becomes slow after page 50, which is reported in KT-948 booking search slow on large practices. The cause is the OFFSET query described above. A plain fix would add an index and keep OFFSET, but OFFSET would still read every skipped row.

    The new index matters as much as the query. INC-2307 booking outage of 29 October 2026 was caused by a missing index: the database fell back to a full table scan and the booking service went down. Migration V57 search index adds an index on slots(practice_id, start_time, id), which matches the search filter (practice) and the new sort order (start time, then ID), so the keyset query can be answered from the index.

    Risk: the total count is gone

    Breaking change in the response. The search response no longer contains the total number of results. Keyset pagination does not need it, and computing it would need a count over all matching rows, the kind of expensive query this change removes.

    The author checked with the mobile app team: mobile app 3.2 uses the count only for a label. The write-up does not say what that label shows after the change, and it names no other consumers of the count. A reviewer who knows of another client that reads the total count should say so on the pull request.

    How to review

    1. Read the service change

      Check the diff in BookingSearchService.java above: the cursor condition, the sort on start time then ID, and the extra row.

    2. Check the migration against the query

      Confirm that the index in V57__search_index.sql (practice_id, start_time, id) matches the filter and sort order of the new query, so that the search cannot fall back to a full table scan as in INC-2307 booking outage.

    3. Run the integration tests

      Run the test class BookingSearchServiceIT with the project's usual test command. All six new tests should pass, including the one for a stable order across pages.

    4. Try the endpoint

      Request the first page with five results, then repeat the request with the nextCursor value from each response until no further cursor comes back. No slot should appear twice.

      GET /bookings/search?practice=17&size=5

    5. Check the API documentation

      Read the changes in docs/api/booking-search.md and check that they describe the parameters, the cursor and the removed total count.

    Glossary

    OFFSET pagination
    Pagination that skips a number of rows (page × size) before returning the next page. The database still reads every skipped row, so later pages get slower.
    Keyset pagination
    Pagination that continues after the last row seen, identified by its sort key (here start time and ID), instead of skipping a row count. Every page costs about the same.
    Cursor
    An opaque marker returned with each page (here nextCursor) that tells the server where the next page starts.
    Full table scan
    A query that reads every row of a table because no index matches its filter and order.
