    How a booking request flows through the code

    A booking request travels in a straight line: the REST endpoint POST /bookings hands it to BookingService.book(), which takes a 30-second Redis lock on the time slot, checks that the slot is still free, saves the booking and publishes a BookingCreated event that sms-service uses to schedule the reminder SMS. Before changing this path, read the three gotchas below: keep the lock longer than the database timeout, expect a taken slot to come back as HTTP 409, and never call book() inside another transaction.

    Prepared on 3 November 2026 for Priya, who is joining the booking team. The code excerpt is BookingService.java as of commit 7c41e9a on master.

    The flow at a glance

    Step by step

    1. The endpoint receives the request

      BookingResource.java exposes POST /bookings. It passes the request on, as a BookingRequest, to BookingService.book(), where the booking logic lives.

    2. The service locks the slot

      book() first calls SlotLock.acquire(slotId), which takes a Redis lock on the requested slot with a 30-second time to live (TTL). While one request holds the lock, a second request for the same slot cannot get past this line. The lock is opened in a try-with-resources block, so it is released as soon as book() returns or throws.

    3. The service checks the slot is still free

      With the lock held, slots.findAvailable() looks the slot up again. If it is no longer available, the method throws SlotTakenException, which the API returns as HTTP 409 (see gotcha 2). Checking only after locking is what makes the check trustworthy: nobody else can book the slot between the check and the save.

    4. The booking is saved

      BookingRepository.save() writes the new booking, built with Booking.from(req, slot). This is the database call whose timeout must stay shorter than the lock's 30 seconds (gotcha 1).

    5. A BookingCreated event is published

      BookingEventPublisher.publish() announces the new booking with a BookingCreated domain event that carries the booking's ID. This also happens while the lock is still held.

    6. sms-service schedules the reminder

      sms-service is a separate service. It receives BookingCreated and schedules the reminder SMS for the booking.

    The key method: BookingService.book()

    This is the whole use case, taken from BookingService.java at 7c41e9a master. The highlighted lines are the ones the notes below explain.

    public Booking book(BookingRequest req) {    try (SlotLock lock = slotLock.acquire(req.slotId())) {        Slot slot = slots.findAvailable(req.slotId())            .orElseThrow(() -> new SlotTakenException(req.slotId()));        Booking booking = repository.save(Booking.from(req, slot));        events.publish(new BookingCreated(booking.id()));        return booking;    }}
    1. AThe lock is taken first and lives exactly as long as the try block. Nothing in this method runs for that slot without it.
    2. BThe availability check runs inside the lock. orElseThrow turns "no free slot" into SlotTakenException, which becomes HTTP 409.
    3. CThe save is the slow, database-bound step. If it took longer than the lock's TTL, the lock would expire while the booking is still being written.
    4. DThe event carries only the booking ID.
    5. EThe closing brace of the try block releases the lock, on success and on any exception.

    Three gotchas

    1. The lock TTL must be longer than the database timeout

    The Redis lock expires after 30 seconds whether or not book() has finished. If a database call could run longer than that, the lock would vanish mid-booking and a second request could lock and book the same slot. Keep the database timeout below the lock TTL, and if either value changes, change the other with it. The team decision behind the locks is ADR-011 Redis slot locks. The current database timeout value is not given in this walkthrough; check the service configuration before relying on a number.

    2. SlotTakenException becomes HTTP 409

    ExceptionMappers.java maps SlotTakenException to HTTP 409 Conflict. That way a taken slot reaches the caller as a conflict, not as a server error. Signal a taken slot by throwing this exception, and update the mapping if the exception is renamed.

    3. Never call book() inside another transaction

    This has caused a production bug. Calling book() from inside another database transaction caused the double bookings in BUG-3120 double bookings, June 2026. Call book() on its own, outside any surrounding transaction.

    A likely reason, to be confirmed with the team because the source does not describe the mechanism: inside an outer transaction, the saved booking is only committed when that outer transaction ends, which is after book() has returned and released the lock. In that gap, a second request can take the lock, see the slot as still free and book it too.

    Glossary

    Architecture decision record (ADR)
    A short document that records one technical decision, its context and its consequences, so later readers know why the code is the way it is.
    Domain event
    A message that says something has happened in the domain, here that a booking was created. Other services, such as sms-service, react to it without the booking service calling them directly.
    HTTP 409 Conflict
    An HTTP status code meaning the request conflicts with the current state of the resource. The booking API returns it when the requested slot is already taken.
    Redis lock
    A lock stored in Redis, an in-memory data store, so that every instance of the booking service sees it, not only the process that took it.
    Time to live (TTL)
    How long Redis keeps a key, here the slot lock, before deleting it automatically. The slot lock's TTL is 30 seconds.
    Try-with-resources
    A Java try (…) block that closes the resource it opens when the block ends, whether it ends normally or with an exception. book() uses it to release the slot lock.
