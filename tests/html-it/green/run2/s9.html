Incident postmortem

    Booking API slowdown on 29 October 2026

    On 29 October 2026 the booking API was slow or failing for 29 minutes, from 09:12 to 09:41 CET, and about 1,140 booking attempts failed; no data was lost. The cause was a missing database index: the new appointment search from PR 402 new appointment search query shipped in release 8.4.0.0 without its planned index migration, so every search read the whole slots table and used up the database connection pool. Rolling back to release 8.3.2.4 ended the incident. Three actions close the gaps, the last one due on 28 November 2026; product management needs to do nothing beyond following them.

    Blameless postmortem of incident INC-2307 booking API slowdown, severity SEV-2 severity level, written for engineering and product management. All times are Central European Time (CET).

    Impact

    Duration29 minutes of slow or failed booking (09:12 to 09:41 CET)
    Failed bookingsAbout 1,140 failed booking attempts
    Worst latencyp95 latency 9.8 s, against 0.4 s normally (about 25 times slower)
    Data lossNone

    Patients and practice staff trying to book an appointment during those 29 minutes either waited many seconds or got an error. Bookings that went through were stored correctly.

    Cause

    The appointment search query added in PR 402 new appointment search query filters slots by practice and start time. It needs an index on slots(practice_id, start_time). That index was in the migration plan, but the migration file that creates it was missing from the pull request, so release 8.4.0.0 went live without it.

    Without the index, every search request did a full table scan. Each slow query held a database connection for much longer than usual, so the database connection pool filled up to its maximum of 50. New requests then had to wait for a free connection, and many timed out.

    Two safety nets did not catch the gap before release: load test LT-12 booking load test does not exercise search, and no automated check looks at query plans. The cause is this process gap, not any one person.

    What went well and what went badly

    Went well

    • The alert fired within 2 minutes of the slowdown starting.
    • Rollback runbook RB-04 rollback runbook worked exactly as written.

    Went badly

    • Load test LT-12 booking load test does not cover search, so the slow query was not visible before release.
    • The index was in the migration plan, but the migration file was missing from the pull request, and nothing in review or CI noticed the difference.

    Glossary

    Database connection pool
    A fixed set of open database connections that the booking API shares between requests; its maximum here is 50.
    Full table scan
    The database reads every row of a table to answer one query; slow on large tables.
    Index
    A database structure that lets a query find matching rows directly instead of reading every row in the table.
    Load test
    An automated test that sends a realistic volume of traffic to a system to see how it behaves under load.
    p95 latency
    The response time that 95 % of requests stay under; the slowest 5 % take longer.
    Query plan
    The database's description of how it will run a query, including whether it uses an index or scans the whole table.
    Rollback
    Putting the previous release back into production to undo a faulty change.
    Runbook
    A written, step-by-step procedure for an operational task, such as rolling back a release.
