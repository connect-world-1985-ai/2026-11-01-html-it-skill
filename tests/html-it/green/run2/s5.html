Backend onboarding

    Your first week as a backend engineer

    By the end of your first week you have shipped your first pull request and shown it to the team in the Friday sync. The eleven tasks below get you there, day by day: tick each one as you finish it, and send the progress message at the bottom of the page to your buddy so they can see where you are.

    Your ticks stay in this browser. This page is a file, so it cannot share anything with other people: your buddy does not see your ticks, and opening the file on another computer starts empty. To keep your buddy up to date, copy the progress message into your Teams chat with them, for example at the end of each day.

    Your week at a glance

    Each day builds on the one before: you need working accounts and the virtual private network (VPN) to build the code, a working build to understand an issue, and an issue to ship a pull request. If a day runs long, carry the open tasks into the next day rather than skipping ahead.

    Day by day

    1. Day 1: get set up Not started

      • Everything else this week runs on it.

      • The VPN lets your laptop reach the team's internal systems; set it up before the accounts so you can check that each one works.

      • Jira is the issue tracker, Bitbucket hosts the code and its pull requests, and Teams is for chat and calls. Done means you can sign in to all three.

      • The team's onboarding document on how the team works. Where it is stored is not given here; ask your buddy for the link.

    2. Day 2: build and test the core project Not started

      • A local build is how you will test your own changes from Day 3 on. Build instructions are not part of this checklist; your buddy can point you to them.

      • The integration tests need Docker, so install it and make sure it is running first. Done means the tests run to the end on your laptop.

      • Working on the code together with your buddy is the fastest way to learn how the project fits together, and the right moment to ask about anything the build or the tests left unclear.

    3. Day 3: choose your first piece of work Not started

      • A good first issue is small enough to ship by the end of the week. Choose one you can finish by Day 5; your buddy can help you judge the size.

      • This architecture decision record (ADR) explains why the system uses event sourcing. Reading it before you change code helps your first change fit the way the system stores data.

    4. Days 4 and 5: ship and demo Not started

      • Open a pull request in Bitbucket for your good first issue and see it through review.

      • Show the team what you changed and why in the Friday sync. A few minutes is enough: the issue, your change, and how you tested it.

    Glossary

    Architecture decision record (ADR)
    A short document that records one architecture decision, the reasons for it and its consequences.
    Buddy
    The teammate who accompanies you through your first week and should be kept up to date on your progress.
    Docker
    A tool that runs software in isolated containers; the integration tests need it.
    Event sourcing
    Storing every change to the data as an event in a log, and deriving the current state from those events, instead of keeping only the latest state. ADR-007 why we use event sourcing explains the team's reasons.
    Friday sync
    The team's Friday meeting, where new joiners demo their first pull request. Time and place are not given in the checklist.
    Good first issue
    An issue the team has marked as small and well suited to someone new to the code.
    Integration tests
    Tests that run the service together with the systems it depends on, rather than one class or function on its own.
    Pull request
    A request in Bitbucket to merge your change into the main code, where teammates review it first.
    Virtual private network (VPN)
    A private network connection to the company's internal systems from your laptop.
