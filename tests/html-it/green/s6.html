Order service onboarding

    Event sourcing in the order service

    The order service does not store what an order looks like now; it stores every change that ever happened to it, as a list of events, and works out the current state by replaying that list. The team chose this design in ADR-007 decision to use event sourcing for orders because medical billing needs a complete history. If you come from CRUD backends, read the next two sections first; they change what "saving" an order means.

    Prepared 3 November 2026 for backend engineers joining the order service team.

    Snapshot versus log

    In a CRUD service, an order is one row. When the payment arrives, the row's status changes from "placed" to "paid", and the old value is gone. The database always knows the present and forgets the past.

    In an event-sourced service, nothing is overwritten. Each change is appended as a new event to an append-only log: OrderPlaced, then PaymentCaptured, then OrderShipped. The log is the source of truth. "The order is paid" is not stored anywhere directly; it is a conclusion you reach by reading the log.

    How an order moves through the service

    Every change follows the same path, from a request on the left to a screen on the right. The left half decides and records; the right half prepares data for reading.

    1. A command asks for a change

      A command such as "capture payment for this order" arrives. It is a wish, not a fact: it can still be refused.

    2. The aggregate decides

      The aggregate for that order replays the order's events to learn its current state, then checks the rules, for example "an order cannot be shipped before it is paid". If the command is allowed, the aggregate produces one or more new events.

    3. The event store records the fact

      The new event, such as PaymentCaptured, is appended to the order's log in the event store. From this moment it is history and is never edited.

    4. Projectors build read models

      A projector picks up the new event and updates one or more read models: the order list, the invoice view. Each read model is shaped for one screen, so reads are simple and fast.

    5. The UI reads the read model

      Screens never replay events themselves; they query a read model. Because projectors run after the event is stored, a screen can briefly show the previous state. That short delay is called eventual consistency.

    Worked example: replaying one order

    #Event (example)RecordedState after this event
    0no events yet–The order does not exist.
    1OrderPlaced: 2 items, 120.00 EUR2026-02-28Placed; 120.00 EUR open; not shipped.
    2PaymentCaptured: 120.00 EUR2026-03-01Paid; 0.00 EUR open; not shipped.
    3OrderShipped: handed to the carrier2026-03-03Paid; 0.00 EUR open; shipped.

    This is also how a temporal query works. To answer "what did this order look like on 1 March?", replay only the events recorded up to the end of 1 March: rows 1 and 2. The answer is "paid, not yet shipped". A CRUD table cannot answer that question, because it overwrote "paid" with "shipped" on 3 March.

    In code, replaying is a fold over the events: start from an empty state and apply each event in order. The sketch below is pseudocode, not the service's real code.

    state = empty order
for each event in log(order), oldest first:
    state = apply(state, event)   # OrderPlaced sets items and total, PaymentCaptured marks it paid
return state

    Why the team chose it

    The decision record ADR-007 event sourcing for orders, written in March 2025, gives three reasons:

    • A full audit trail for medical billing. Billing must be able to show what changed and when. With event sourcing, the history is not an extra audit table that can drift from the data; it is the data.
    • Read models can be rebuilt. A new screen, or a fix to a broken one, means writing or correcting a projector and replaying the log into a fresh read model. Old data does not need a migration.
    • Temporal queries. Questions like "what did this order look like on 1 March?" are answered by replaying up to that date, as in the example above.

    What it costs

    Event sourcing is not free. The decision record names three costs you will meet in daily work.

    Event schemas must be versioned

    Events are never rewritten, so an OrderPlaced event stored in 2025 keeps its 2025 shape forever. When you add or rename a field, the code must still read every older version. Treat an event's shape like a public API: change it carefully and on purpose.

    Screens can lag behind for a moment

    Projectors update read models after the event is stored, so the UI may briefly show the old state. Design screens and tests with that delay in mind; for example, a test should not read the order list immediately after a command and expect the new status.

    Replays get slower as logs grow

    An order with thousands of events would take longer and longer to rebuild. The service therefore saves a snapshot every 500 events. To rebuild an order, the aggregate loads the latest snapshot and replays only the events after it, at most 499.

    Check your understanding

    Try each question before opening the answer.

    A customer's delivery address changes. Do you update the order's address field?

    No. The change is recorded as a new event appended to the order's log. The current address is whatever the replay produces; the old address stays in the history.

    The order list shows "placed" one second after the payment succeeded. Is that a bug?

    Not necessarily. The read model is updated by a projector after the event is stored, so a short delay is expected (eventual consistency). A delay that does not go away is worth investigating.

    The invoice view shows a wrong total for every order. How do you fix the data?

    Fix the invoice projector, then rebuild the invoice read model by replaying the events. The events were never wrong, so nothing in the event store changes.

    An order has 1,230 events. How many does the aggregate replay to rebuild it?

    230. It loads the snapshot taken at event 1,000 (snapshots are taken every 500 events) and replays the 230 events after it.

    Glossary

    Aggregate
    The object that owns one order's business rules. It rebuilds its state from that order's events and decides whether a command is allowed.
    Append-only log
    A log you can only add to at the end; existing entries are never edited or removed.
    Command
    A request to change something, written as an instruction (capture payment, ship order). It can be rejected.
    CRUD
    Create, read, update, delete: the usual style where each table row holds the latest state and updates overwrite it.
    Event
    A fact about something that already happened, written in the past tense, such as OrderPlaced. Events are never changed or deleted.
    Event sourcing
    A storage design where the source of truth is the append-only list of events, and current state is derived by replaying them.
    Event store
    The database that holds the append-only event logs; the single source of truth on the write side.
    Eventual consistency
    The read side catches up with the write side after a short delay instead of instantly.
    Projector
    A component that listens to new events and updates a read model from them.
    Read model (projection)
    A table or document shaped for one screen or query, such as the order list or the invoice view, rebuilt from events.
    Snapshot
    A stored copy of an aggregate's state at a given event, so replay can start from there instead of from the first event. The order service takes one every 500 events.
    Temporal query
    A question about the past state of data: what did this order look like on a given date?
