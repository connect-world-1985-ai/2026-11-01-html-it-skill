    Patient portal UI audit

    The user-interface audit of the patient portal for R26.11 patient portal release found one issue on each of the first ten screens. Two of them affect patient safety or privacy: an appointment can be cancelled without confirmation, and the full insurance number is visible on the profile screen. The issues for screens 11 to 40 are still to be filled in. Developers: open one screen page from the table below. Designers: put each PNG export into the assets/ folder under its listed file name, and the screen page shows it.

    Prepared 3 November 2026 for the patient portal developers and designers. The screenshots themselves are not part of this folder yet: PNG files screenshots not provided.

    What the audit found

    The designers captured 40 full-page screenshots and noted one issue per screen. For screens 1 to 10 the issues are known and fall into five kinds. This grouping was added for the overview; the original audit notes do not group the issues and give no severity.

    • Safety and privacy (2 screens): cancelling an appointment needs no confirmation, and the insurance number on the profile screen is not masked. These are the ones to fix first.
    • Accessibility (3 screens): a password field without a visible label, unread messages marked only by colour, and settings toggles that do not say what on and off mean.
    • Consistency (2 screens): three competing primary buttons on the dashboard, and two date formats on the appointments list.
    • Layout (1 screen): long messages overflow on a phone screen 390 px wide.
    • Missing information (2 screens): no file sizes on downloads, and no empty state guidance when a help search finds nothing.

    Screens 11 to 40

    The audit notes say that screens 11 to 40 follow the same pattern, one issue per screen, but neither their file names nor their issues are written down yet. They are left out of this folder rather than guessed. Once the designers send the list, each screen gets a page in parts/ in the same format as screens 1 to 10.

    How screenshots get into the pages

    The screenshots stay as separate PNG files so that the designers can keep replacing them with new Figma exports; copies inside the HTML would go out of date. Embedding all 40 would also produce one file of about 70 MB, too large to attach to a Teams message or an email.

    1. Save each PNG into the assets/ folder with exactly the file name in the table, for example assets/01-login.png.
    2. Open the screen page. It shows the screenshot if the file is there, and a labelled “image not provided” placeholder if not.
    3. To share, zip the whole folder. Readers unzip it and open index.html.

    Glossary

    Primary button
    The one button on a screen styled as the main action, so the user knows the expected next step.
    Empty state
    What a screen shows when there is nothing to list, for example a search with no results. A good empty state says what to try next.
    Masking
    Showing only part of a sensitive value, for example the last four digits of an insurance number, with the rest replaced by dots.
