The problem: one nightly job, late reminders, manual retries

6 % of reminders arrive late.

Reminders are sent by a nightly cron job in the core service. When a reminder fails, nobody retries it automatically: someone has to resend it by hand, as tracked in KT-955 late reminders and manual retries. Because all reminders go out in the same run, the job also causes a load peak at 02:00 Time zone to be confirmed.

Three symptoms of one cause: everything happens in one batch at night. Mention that the time zone of the 02:00 peak is not stated in the proposal.

How option B works

Instead of one batch at night, the core service puts each reminder on a message queue. A consumer takes reminders only as fast as it can send them; this back-pressure spreads the load instead of concentrating it in one run. A failed send goes back to the queue and is tried again, so no one has to resend it by hand. RabbitMQ is already in use for sms-service, so the platform gains no new kind of infrastructure.

Why B over A and C

Option A is cheapest, but only half a fix

Adding retries to the cron job takes 3 days and removes the manual resends. The load peak at 02:00 stays, because all reminders still go out in one nightly run.

Option C is quick, but has a bill and a compliance hurdle

An external provider takes about 1 sprint, then costs about 1,800 EUR per month. Patient data would leave our hosting, so under SEC-20 patient data stays in EU-hosted systems it needs a data processing agreement first.

Option B costs most effort, and fixes both problems

About 2 sprints of work, plus a runbook so that operations can run the queue. In return, retries and back-pressure are part of the design rather than added on top.

Be honest that B is the largest effort. The argument is that it is the only option that removes both the manual retries and the night peak without sending patient data out.

Glossary

Back-pressure
A receiver slowing the flow of work to the rate it can handle, instead of being overloaded.
Cron job
A job that the server starts automatically on a fixed schedule, here once a night.
Data processing agreement
A contract that sets how an outside company may handle personal data on our behalf.
Message queue
A buffer that holds messages until a receiving program is ready to process them.
RabbitMQ
An open-source message broker; our sms-service already uses it.
Runbook
A written guide that tells operations staff how to run, monitor and repair a system.
