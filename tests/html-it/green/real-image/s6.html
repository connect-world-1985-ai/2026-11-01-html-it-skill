    Event sourcing in the order service

    The order service does not keep one row per order that gets overwritten. It keeps every change to an order as an event in a log that is only ever appended to, and it works out the current state by replaying those events. The team chose this in ADR-007 the decision to use event sourcing for orders in March 2025, mainly because medical billing needs a full audit trail. If you come from CRUD backends, read the worked example below before you change anything in the order service: the habits that work there (update the row, read the row) do not apply here.

    Prepared 4 November 2026 for new backend engineers joining the team.

    A snapshot versus a log

    In a CRUD design, an order is a single record. When the order is paid, the status field changes from "placed" to "paid", and the old value is gone. The record is a snapshot: it is always up to date, and it has forgotten how it got there.

    With event sourcing, the order is a list of facts in the order they happened: the order was placed, the payment was captured, the order was shipped. Nothing in that list is edited or deleted. The current state is not stored as the truth; it is the result of reading the list from the start.

    A bank account works the same way. The bank does not trust a single "balance" number; it keeps every deposit and withdrawal, and the balance is what you get when you add them up. Lose the balance and you can recompute it. Lose the transactions and you cannot.

    From a request to the screen

    Six parts take a change from a user's request to what another user sees. The top row is the write side, which decides and records what happened; the bottom row is the read side, which turns the recorded events into data that screens can show quickly.

    1. A command arrives, for example "capture the payment for this order". A command is a wish; it can still be refused.
    2. The aggregate for that order loads the order's past events, replays them to know the current state, and checks the command against the business rules (you cannot ship an order that has not been paid). If the command is valid, it produces one or more new events.
    3. The new events are appended to the event store. From this moment the change is a fact.
    4. A projector picks up the new events and updates a read model, such as the order list or the invoice view. The result is also called a projection.
    5. The user interface reads from the read model, never from the event store directly, so screens stay fast however long the history gets.

    1. OrderPlaced on 3 February 2025

      State after replay: status placed, payment open, shipment none.

    2. PaymentCaptured on 4 February 2025

      State after replay: status paid, payment captured, shipment none.

    3. OrderShipped on 6 February 2025

      State after replay: status shipped, payment captured, shipment on its way.

    Two things follow from this. First, the order never had a row that said "shipped" until something replayed the three events; the state is computed, not stored. Second, if you stop the replay early you get the order as it was at that moment. That is how the team answers temporal queries such as "what did this order look like on 1 March?": replay only the events dated up to 1 March.

    Coming from CRUD: you will want to "fix" a wrong order by editing it. In the order service you record a new event that corrects it instead. The mistake and its correction both stay in the history, which is exactly what auditors want to see.

    Why the team chose it

    The decision is recorded in ADR-007 event sourcing for the order service, from March 2025. It gives three reasons:

    • A full audit trail for medical billing. Every change to an order, and when it happened, is kept by design, not by a separate audit table that someone might forget to fill.
    • Read models are easy to rebuild. If the invoice view has a bug, or a new screen needs data in a new shape, the team writes or fixes a projector and replays the events into a fresh read model. No data migration of the source of truth is needed.
    • Questions about the past can be answered. Temporal queries such as "what did this order look like on 1 March?" are a replay up to a date, not a forensic search through logs.

    What it costs

    Event sourcing is not free. These are the three costs the team accepted, and what each means for your daily work.

    Event schemas must be versioned

    Events are never rewritten, so an event stored in 2025 must still be readable after the code changes. When you change the shape of an event, you add a new version and keep code that can read the old ones. You cannot simply rename a field as you would in a CRUD table. This is called event schema versioning.

    Screens can lag behind for a moment

    The projector updates read models after the event is stored, not in the same transaction. For a short time, the order list can show the old state while the event store already has the new one. This is eventual consistency between the write side and the projections. Design screens and tests with it in mind: after sending a command, do not assume the read model has already changed.

    Replay gets slower as history grows

    An order with a long history means more events to replay each time the aggregate loads it. The team limits this with snapshots: every 500 events, the current state of the aggregate is saved, and loading starts from the latest snapshot plus the events after it.

    Snapshots taken so far: 2. Events replayed when the order loads: 234, on top of the latest snapshot, instead of all of them.

    This assumes a snapshot at every 500th event, as described above. Without snapshots, every event would be replayed.

    Check your understanding

    An order shows "paid" in the order list, but the event store already has OrderShipped. Is something broken?

    Probably not. The projector has not processed the new event yet; this is eventual consistency. It becomes a problem only if the read model does not catch up.

    The invoice view has shown wrong totals for a month. How is it repaired?

    Fix the projector that builds the invoice view, delete the read model and replay the events into it. The events themselves were correct all along, so nothing in the event store changes.

    A field in PaymentCaptured was badly named. Can you rename it in the stored events?

    No. Stored events are never edited. Add a new version of the event with the better name and keep the code able to read the old version.

    Glossary

    Aggregate
    The object that owns one order's rules. It rebuilds the order from its events, checks a command against the rules, and decides which new events to record.
    Append-only log
    A list that can only grow at the end; entries are never changed or deleted.
    Command
    A request to change something, such as "capture the payment for this order". It can be rejected.
    CRUD
    Create, read, update, delete: a design where each record holds only its current state and changes overwrite it.
    Eventual consistency
    A guarantee that read models will catch up with the event store, but not instantly; for a short time they may show older data.
    Event sourcing
    Storing every change to an object as an event in an append-only log, and deriving the current state by replaying the events.
    Event schema versioning
    Managing changes to the structure of events so that old, stored events can still be read by new code.
    Event store
    The database that holds all events in order. Events are only added, never changed or deleted.
    Projection
    Another name for a read model built from events, or for the process that builds it.
    Projector
    A process that reads new events from the event store and updates one read model from them.
    Read model
    A table or document shaped for one screen or query, built from events by a projector. It can be deleted and rebuilt at any time.
    Replay
    Reading an object's events from the start (or from a snapshot) and applying them in order to compute its state.
    Snapshot
    A saved copy of an aggregate's state at a given event, so that loading starts from the snapshot instead of from the first event. The order service takes one every 500 events.
    Temporal query
    A question about the past state of something, such as "what did this order look like on 1 March?".
