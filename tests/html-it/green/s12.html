Pull request write-up

    Paginate booking search

    PR 437 Paginate booking search replaces OFFSET paging in the booking search with keyset pagination and adds a matching index, so that search stays fast on large practices. It is ready for review. The one behaviour change to judge is that the response no longer contains a total count; the only known user, mobile app 3.2, shows it in a label, and this was checked with the app team.

    Branch feature/KT-948-pagination into master. Background: KT-948 booking search slow on large practices and INC-2307 booking outage of 29 October 2026.

    The key change

    The heart of the pull request is one query in BookingSearchService.java:

    -    return query.offset(page * size).limit(size).fetch();
+    return query.where(cursor.after(lastStartTime, lastId))
+                .orderBy(SLOT.START_TIME.asc(), SLOT.ID.asc())
+                .limit(size + 1).fetch();

    Where. Instead of skipping page * size rows, the query continues after the last slot of the previous page, identified by its start time and ID. The database no longer reads and discards every earlier row, which is what made deep pages slow.

    Order by. Sorting by start time and then ID gives every slot a unique position, so slots with the same start time are neither repeated nor skipped between pages. The new integration tests check this stable order across pages.

    Limit. The query reads one row more than the page size. The source does not say what the extra row is for; reviewers should confirm that it only decides whether a next page (and a nextCursor) exists and is not returned to the client.

    Why

    With OFFSET, the database reads every skipped row before returning a page, so the cost grows with the page number. Booking search gets slow after page 50 on large practices (KT-948 slow search). The INC-2307 29 October outage showed what a full table scan does to the booking API: that outage was caused by a missing index. The new index on slots(practice_id, start_time, id) matches the new filter and sort order, so each page can be read from the index.

    Glossary

    Keyset pagination
    Pagination that continues after the last row seen (here by start time and slot ID) instead of skipping a number of rows with OFFSET. Its cost does not grow with the page number.
    Full table scan
    A query that reads every row of a table because no index matches its filter and order.
    nextCursor
    The value in a search response that points to the next page; the client sends it back to get that page.
    Opens offline; no network access needed.
