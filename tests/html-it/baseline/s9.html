Booking API slowdown after release 8.4.0.0

Postmortem for engineering and product management

Summary

For 29 minutes on 29 October, booking was slow or failing. The new appointment search query from PR 402 had no index on slots(practice_id, start_time), so every request did a full table scan and filled the database connection pool. Rolling back to 8.3.2.4 restored normal latency. No data was lost.

Root cause

The migration plan included the index on slots(practice_id, start_time), but the migration file was missing from PR 402. Load test LT-12 does not exercise search, so nothing caught the full table scan before release. Under production load the scans kept the database connection pool at 100 % (max 50), and booking requests queued behind them.

What went well, what went badly

Went well

  • The alert fired within 2 minutes.
  • Rollback runbook RB-04 worked as written.

Went badly

  • Load test LT-12 does not cover search.
  • The index was in the migration plan, but the migration file was missing from the PR.

Measured from the 09:12 alert: acknowledged after 3 min, rollback started after 22 min, latency normal after 29 min, root cause found after 53 min.
