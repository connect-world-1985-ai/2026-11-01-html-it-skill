New joiner explainer · Order service

We don't store orders. We store what happened to them.

The order service uses event sourcing. If you come from CRUD backends, this page shows what changes, why we chose it, and what it costs.

ADR-007 · decided 2025-03

The idea in one sentence

We don't keep a row with an order's current state. We record every change as an event, such as OrderPlaced, PaymentCaptured or OrderShipped, in an append-only log. Events are never edited or deleted. To get the current state, we replay the events in order.

What you're used to: a CRUD row

order_idstatuspaid
ORD-1042shipped184.00

Each update overwrites the row. Earlier values, and the reasons they changed, are gone.

What we store: the event log

#eventat
1OrderPlaced28 Feb 09:14
2PaymentCaptured1 Mar 16:40
3OrderShipped3 Mar 11:05

New facts are only ever appended. The row on the left can be computed from this log at any time.

    Reading: projections build read models

    Replaying the log for every screen would be slow, and the log is shaped for writing, not for querying. So projectors listen to new events and keep read models up to date: tables or documents shaped for one screen. In the order service, these include the order list and the invoice view. Both are built from the same events, and either one can be deleted and rebuilt from the log.

    How a change flows through the system

    1. CommandA request to change something, such as "capture payment".
    2. AggregateRebuilds the order from its events, checks the rules, and decides which new events to emit.
    3. Event storeAppends the new events. This is the source of truth.
    4. ProjectorReacts to new events and updates the read models.
    5. Read modelQuery-ready views, such as the order list and the invoice view.
    6. UIReads from the read models, not from the event store.

    Why ADR-007 chose this

    Full audit trail

    Medical billing needs a record of every change and when it happened. The event log is that record.

    Easy rebuild of read models

    Did a projection have a bug, or do you need a new view? Fix the projector and replay the log.

    Temporal queries

    "What did this order look like on 1 March?" Replay the events up to that date. Try it in the demo above.

    What it costs us

    These are the trade-offs you will run into in day-to-day work.

    Event schema versioning

    Old events stay in the log forever. When an event's shape changes, code still has to read every earlier version.

    Eventual consistency

    Read models update after the write. For a short time, the UI can show the state from before a change that has already been recorded.

    Replay time grows

    Orders with long histories take longer to rebuild. We take a snapshot every 500 events, so a rebuild starts from the latest snapshot.

    Words you'll hear

    Event
    A fact that happened, named in the past tense. It is never changed after it is written.
    Event store
    The append-only log of events and the source of truth for orders.
    Aggregate
    The order as the write side sees it: rebuilt from events, used to validate commands.
    Projection / projector
    Code that turns events into a read model.
    Read model
    A view optimised for queries, such as the order list. It can be thrown away and rebuilt.
    Snapshot
    Saved state at a point in the log, taken every 500 events, so replay doesn't start from event 1.
    Eventual consistency
    Read models catch up with the event store shortly after each write, not instantly.
