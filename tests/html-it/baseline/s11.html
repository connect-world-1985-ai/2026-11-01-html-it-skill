Booking team onboarding

How a booking request flows through the code

A walkthrough for Priya, who joins the booking team next week. It follows one POST /bookings from the HTTP layer to the SMS reminder.

The path

Request flow

Loading diagram. The same flow is listed step by step below.

  1. BookingResource.java receives POST /bookings.
  2. BookingService.book() runs the booking.
  3. SlotLock.acquire(slotId) takes a Redis lock on the slot with a 30 s TTL.
  4. BookingRepository.save() writes the booking.
  5. BookingEventPublisher.publish(BookingCreated) announces it.
  6. sms-service schedules the reminder.
Key code

Inside BookingService.book()

BookingService.java commit 7c41e9a on master Snapshot. The file may have changed since. 
public Booking book(BookingRequest req) {
    try (SlotLock lock = slotLock.acquire(req.slotId())) {
        Slot slot = slots.findAvailable(req.slotId())
            .orElseThrow(() -> new SlotTakenException(req.slotId()));
        Booking booking = repository.save(Booking.from(req, slot));
        events.publish(new BookingCreated(booking.id()));
        return booking;
    }
}
  • L2The try-with-resources block takes the Redis slot lock and releases it when the block exits. The lock has a 30 s TTL. See gotcha 1.
  • L3–4If the slot is no longer available, SlotTakenException is thrown. The client gets HTTP 409. See gotcha 2.
  • L5BookingRepository.save() persists the booking while the lock is still held.
  • L6BookingCreated is published. sms-service schedules the reminder from this event.
Before you change this code

Gotchas

  1. 1. The lock TTL must be longer than the DB timeout. Decision record: ADR-011 "Redis slot locks".
  2. 2. SlotTakenException becomes HTTP 409. The mapping lives in ExceptionMappers.java.
  3. 3. Never call book() inside another transaction. Doing so caused the double bookings in BUG-3120 (2026-06).
