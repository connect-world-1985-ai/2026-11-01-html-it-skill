Research verdict

    Can one HTML file do it all?

    Yes, for nearly everything the team shares. One self-contained HTML file can hold a review, a plan, an explainer, a deck, a clickable prototype, a board of UI sketches or a small interactive tool. It opens offline in any browser, and it can be attached to a Teams message or an email or stored in SharePoint. It stops being the best answer in four cases: heavy raster media, state that people must share, assets people must keep editing, and live data.

    Research verdict for the team, 2026-11-03. Basis: the 20 single-file examples in this repository, the HTML research report, and the html-it skill tests (16 scenarios, each passing in two consecutive runs).

    The rule we use: one file by default. Split into a small folder (multi-part) only when the file would pass about 20 MB or when assets must stay editable. For shared state or live data, a file is the wrong tool: share a dated snapshot page and link to the system that holds the live data.

    What one file can carry

    A browser treats a local HTML file as a full application. Everything below works from a file opened by double-click, with no server and no internet connection:

    • Documents, reviews, plans and explainers. Headings, a table of contents, popovers that explain references, collapsed appendices.
    • Decks. Arrow keys move between slides, a counter shows the position, and printing gives every slide as a page.
    • Clickable multi-screen prototypes. Each screen is a state in the same file; buttons switch between them.
    • Boards of many UI sketches. Each sketch runs in its own iframe srcdoc, so the sketches' styles cannot clash with each other or with the page.
    • Interactive tools, charts and diagrams. Charts and diagrams are drawn as inline SVG, so they stay sharp, follow the light or dark theme and need no library.

    Content kinds, one by one

    "Yes" means one file is the right default. "With care" means one file works if the page follows a rule from the html-it skill. "No" means one file cannot do the job alone.

    Where one file stops being the best answer

    1. Heavy raster media

    Images inside the file are stored as base64 data URIs, which makes them about 33% larger. Forty full-size screenshots of about 1.3 MB each are 52 MB as PNG files and about 70 MB inside a page. Typical email attachment limits are about 20 to 25 MB. Video makes this worse.

    Rule: past about 20 MB, compress the media, link to it, or use a multi-part folder.

    2. State that must be shared or saved

    A page can remember things with localStorage, but that storage lives in one reader's browser on one computer. Votes, comments, sign-up sheets and edits made together need a server or a platform such as SharePoint or Confluence.

    Rule: out of scope for the file. The page says so where the reader meets the limit and offers a way that works, for example a vote line to paste in the team channel.

    3. Assets people must edit separately

    Source images, design files and data sets that someone will reuse or keep editing go stale once they are embedded.

    Rule: ship them next to the page, in a multi-part folder, and link them by relative path.

    4. Live data

    A page that must open offline cannot fetch live data.

    Rule: show a snapshot with the date it was taken, and link to the live system.

    How to decide: one file or a folder

    A multi-part folder still works offline: an index.html hub, one page per part, the editable originals in assets/, all linked by relative paths. Zipped, it travels like a single attachment.

    Why the page must open offline

    A page could load its fonts and libraries from a CDN when it opens. We decided against it: every html-it page makes zero network requests when it opens. Four reasons:

    1. Reachability in mainland China. Google Fonts is blocked, and a page that waits for its font stylesheet can hang while loading. jsDelivr has been unreliable since it lost its China ICP licence in late 2021. unpkg is slow or unreliable. cdnjs is usually reachable but sometimes slow. The fast China mirrors BootCDN and Staticfile are run by the entity behind the 2024 polyfill.io supply-chain attack, so we do not trust them.
    2. Security. Every CDN script is third-party code running next to internal content: code, incidents and designs. The polyfill.io attack spread exactly this way.
    3. Durability. A page opened from an old Teams thread a year later still works; CDN addresses and versions can disappear.
    4. Proxies. Corporate proxies may block CDNs.

    Size is a smaller problem than it looks, because the agent writing the page does the rendering. Hand-drawn SVG replaces Mermaid (about 3 MB minified). Code highlighting is written into the HTML at build time, which replaces highlight.js. Chart.js (about 200 KB) is inlined only for truly interactive data. A typical page is 30 to 150 KB; the worst case with a heavy library inlined is about 3 MB, which is still fine for Teams or email.

    When a library is truly needed, the agent downloads one pinned version while building the page (from cdnjs or the npm registry; npmmirror inside China) and puts it inside the file. The reader's browser never fetches it.

    These CDN facts are an assessment from knowledge up to mid-2026, not measurements. Reachability from inside mainland China was not tested.

    How the html-it skill applies this verdict

    • Single file by default. The skill's first hard rule: all CSS, JavaScript, fonts and images inside the file, nothing loaded from the internet.
    • The size gate. When the estimated size passes about 20 MB, or assets must stay editable, the agent asks "single file with compressed media, or multi-part?" and gives the estimate. In the tests, the 40-screenshot audit (about 70 MB embedded) became a hub plus one page per screen.
    • Honest limits. When the content needs shared state or live data, the page says what it cannot do and offers a way that works. It never fakes the feature and never publishes the page to a hosting service to get around the limit.
    • The checker enforces the network rule. scripts/check_html.py fails any page that loads a script, stylesheet, font, image or fetch from the network. It also fails bare references and missing titles, language or alt text.

    Glossary

    Self-contained HTML
    An HTML file that carries all of its CSS, JavaScript, fonts and images inside itself, so it needs nothing else to open.
    Data URI
    A URL that carries the file's data itself (for example data:image/png;base64,…), so no separate file or download is needed.
    Base64
    A way to write binary data, such as an image, as plain text. It makes the data about 33% larger.
    iframe srcdoc
    An iframe whose whole HTML document is written into its srcdoc attribute. Each sketch gets its own styles and scripts, isolated from the page and the other sketches.
    CDN
    Content delivery network: servers that host common files such as JavaScript libraries and fonts so many sites can load them from one place.
    Multi-part
    A folder with index.html, a parts/ folder of pages and an assets/ folder, linked by relative paths. Zipped, it is shared like one file and still opens offline.
